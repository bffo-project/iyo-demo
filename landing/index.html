iyo demo

The same small vocabulary, built twice by the same version of iyo. Identical inputs and identical commands; only --theme differs.

    What iyo produces with nothing configured.

    A house style supplied as a directory of overrides.

What to look at

  • Any term page, then the .md, .ttl and .jsonld files sharing its stem.
  • llms.txt at each site root, written for agents rather than people.
  • manifest.json, which describes the content negotiation the site would need.
  • a11y/, the build's own accessibility audit, recorded as data.

What this demo cannot show

GitHub Pages serves files and cannot negotiate content, so asking these sites for text/turtle will not redirect you to the Turtle file. That is a property of the host, not of iyo: the negotiation contract is in each site's manifest.json, and iyo compiles it into configuration for hosts that can act on it. Both sites are therefore built with --link-style file, so links point at documents that exist.

Pointed at this deployment, iyo’s own conformance gate (iyo conform) reports 16 of 54 cases passing. Every one that passes is a negative case, a path that must not resolve, which a file host gets right. All 38 that need negotiation fail: no Vary: Accept, no Link signposting, and Accept: text/turtle answered with HTML instead of a redirect. That is the gate working, not the tool failing.

The vocabulary is a small sample written for this demo, and describes nothing real. Its terms are identified by example.org IRIs, which do not resolve anywhere. Both sites publish those same identifiers, which is the separation iyo is built around: what a term is does not change because its documents are served from somewhere else.
